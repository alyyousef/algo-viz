**BigQuery** is a separated-storage-and-compute warehouse. Tables live in datasets (region-bound). Queries compile to a Dremel tree of execution slots. **On-demand** bills bytes processed; **editions / reservations** bill slot-hours. There is no index you tune like OLTP — clustering, partitioning, and column pruning are the physical design.

## 1. Deep Dive and Mechanics

**Storage.** Capacitor columnar format, optional time-travel and fail-safe. Partition by time or integer range; cluster by a few high-cardinality filters. Streaming inserts vs batch load vs BigLake external tables.

**Slots.** A slot is a unit of compute. On-demand shares a pool; reservations isolate. A query that explodes a join can consume a reservation and stall neighbors.

**SQL.** Standard SQL, scripting, materialized views, BI Engine for Tableau/Looker caches. UDFs and remote functions exist; they are easy to make expensive.

**Governance.** Column-level security, row filters, authorized views, and policy tags (DLP). The dataset is the IAM boundary most teams start with — usually too coarse.

**Jobs.** Every query is a job with a cache (24h, same text + same data). Cache hits are free-ish; they are not a correctness tool if data changed.

<Callout icon="error" title="SELECT star on a 40-column event table">
On-demand price tracks columns and rows scanned. Partition + select the columns you need. A dashboard that scans raw events hourly is a finance incident.
</Callout>

## 2. Mathematical / Theoretical Foundation

Bytes billed ≈ sum of columns read × rows after partition prune. Clustering helps when filters match cluster keys; it is not a guarantee.

Cost comparison: on-demand favors rare, selective queries. Reservations win at high, steady concurrency. Slot contention is a scheduling problem: queue time vs fairness.

## 3. Real-World Implementation

```sql
CREATE TABLE shop.sales
PARTITION BY DATE(sold_at)
CLUSTER BY customer_id
AS SELECT * FROM shop.sales_stage;

SELECT customer_id, SUM(amount)
FROM shop.sales
WHERE sold_at >= '2026-01-01'
GROUP BY 1;
```

The `WHERE` on `sold_at` is what makes the partition prune. Without it you read every day.

## 5. Interview Prep

**Q: Partition vs cluster?**
**A:** Partition is a coarse prune (day, month, integer bucket). Cluster sorts within partitions for a few filter/join keys. You often want both.

**Q: BigQuery vs Snowflake vs Synapse?**
**A:** All separate storage/compute. BigQuery’s default is fully serverless on-demand. Snowflake warehouses are explicit. Synapse dedicated pools are MPP you pause. Interviews want this distinction, not a brand war.

**Q: How do you cap spend?**
**A:** Custom quotas, maximum bytes billed per query, reservations, and authorized views so analysts cannot touch raw.

## 6. Production Use Cases

- Event lake queried in place via BigLake plus curated warehouse tables.
- Streaming inserts for operational analytics with a  minutes-level SLA.
- Authorized views for PII: analysts see aggregates, not emails.

<Callout icon="tip" title="Require a partition filter">
Table options can require a partition filter in the `WHERE` clause. Turn that on for large tables so a junior SQL cannot unpartition the bill.
</Callout>
