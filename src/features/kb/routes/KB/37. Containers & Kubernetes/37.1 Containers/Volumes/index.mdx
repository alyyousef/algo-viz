A container's writable layer dies with the container. **Volumes** are how data escapes that fate. Docker offers named volumes (daemon-managed directories), bind mounts (you pick the host path), and tmpfs (memory). Databases, uploaded files, and caches each want a different one.

## 1. Deep Dive and Mechanics

**Named volume.** `docker volume create pgdata` makes a directory under Docker's graph (often `/var/lib/docker/volumes/`). You mount it at `/var/lib/postgresql/data`. The path on the host is Docker's problem. Backups use `docker run --volumes-from` or a volume plugin (EFS, NFS, cloud disks).

**Bind mount.** `-v /home/dev/src:/app` maps an exact host path. Great for live-reload. Fragile in production: permissions, SELinux labels (`:Z` on Fedora), and Desktop's VM file-sharing slowness.

**tmpfs.** `-v /run:type=tmpfs` (or `--tmpfs`) keeps secrets and scratch off disk. Gone on stop.

**Anonymous volumes.** A Dockerfile `VOLUME /data` plus a run without a named mount creates a random-hash volume. Easy to leak unused volumes; `docker volume prune` after you understand what is dangling.

**Ownership.** The process uid inside the container must be able to write the mount. Rootless Podman and non-root Docker users hit this first. Fix with uid maps or a matching `user:` in Compose.

<Callout icon="warning" title="VOLUME in a Dockerfile is sticky">
Downstream images inherit the VOLUME instruction. You can surprise yourself with anonymous volumes on paths you did not mount. Prefer documenting mounts in Compose, not baking VOLUME unless you are a database image.
</Callout>

## 2. Mathematical / Theoretical Foundation

**Lifecycle independence.** Let C be a container id and V a volume id. Deleting C does not delete V unless you pass `-v` to `docker rm`. The writable layer's lifetime is subset of C; V's lifetime is operator-controlled.

**Consistency.** A bind mount is the host page cache. A named volume on Desktop may cross a VM virtiofs/9p boundary — extra copies, extra latency. That is why Postgres on a Mac bind mount feels drunk and on a Linux named volume does not.

## 3. Real-World Implementation

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
  api:
    image: myorg/api:1.4
    volumes:
      - ./src:/app/src
      - cache:/app/.cache
volumes:
  pgdata:
  cache:
```

The API bind-mounts source for development. Postgres uses a named volume so a compose down/up does not wipe the cluster.

## 5. Interview Prep

**Q: Where did my database go after I removed the container?**
**A:** If it lived in the writable layer, it is gone. If it was a named volume and you did not `docker rm -v`, the volume is still there — attach it to a new container.

**Q: Bind mount versus volume in production?**
**A:** Named or plugin volumes. Binds couple you to host layout and are harder to migrate.

**Q: Why is I/O slow on Docker Desktop?**
**A:** The files live on macOS/Windows and are projected into a Linux VM. Use a named volume (data inside the VM) for heavy write workloads.

## 6. Production Use Cases

- **Stateful single-host Compose** (Postgres, Redis persistence).
- **CI caches** as named volumes between jobs on the same runner.
- **Secret tmpfs** so tokens never hit the graph driver disk.

<Callout icon="tip" title="Name every volume">
Anonymous volumes are how disks fill up with hashes nobody owns. Compose `volumes:` keys are cheap documentation.
</Callout>
