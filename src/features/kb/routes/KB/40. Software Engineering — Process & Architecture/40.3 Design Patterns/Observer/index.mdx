In an e-commerce app, when a `Customer` changes their address, the `ShippingService`, the `BillingService`, and the `MarketingService` all need to know.

## 1. The Polling Anti-Pattern
If the BillingService mathematically polls the Customer object every 5 seconds (`if (addressChanged())`), it burns massive amounts of CPU cycles for no reason.

## 2. The Publish-Subscribe Mechanism
The Observer pattern perfectly solves this.
The `Customer` (the Subject) maintains an internal array of `IObserver` interface pointers.
The three services mathematically "subscribe" by passing their pointer to the Customer: `customer.subscribe(billingService)`.
When the address is updated, the `Customer` iterates over its internal array and mathematically executes `observer.notify(newAddress)` on every object in the list. The services instantly receive the data without polling, and the `Customer` remains decoupled because it only knows it is talking to a generic `IObserver`, not a specific Billing Service. (This is the mathematical foundation of RxJS and Event Listeners in JavaScript).
