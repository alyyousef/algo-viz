If you are programming a Vending Machine, its behavior drastically changes based on its state. If the state is `NO_COIN`, pressing the "Dispense" button must mathematically fail. If the state is `HAS_COIN`, pressing "Dispense" must succeed and change the state to `DISPENSING`.

## 1. The Switch-Statement Nightmare
Developers usually solve this with massive `switch(currentState)` blocks inside every single method (`insertCoin()`, `dispense()`). If you add a new state, you must mathematically update 15 different switch statements, violating the Open-Closed Principle.

## 2. Polymorphic States
The State pattern solves this by converting the States into concrete Objects.
You create an `IState` interface with methods for every action (`insert()`, `dispense()`).
You create concrete classes for the states: `NoCoinState` and `HasCoinState`.
The VendingMachine object just holds a pointer to an `IState` object. When the user presses "Dispense", the VendingMachine blindly delegates the call: `this.currentState.dispense()`.
The `HasCoinState` object executes the logic and mathematically injects the new `DispensingState` object into the VendingMachine, elegantly replacing complex branching logic with polymorphism.
