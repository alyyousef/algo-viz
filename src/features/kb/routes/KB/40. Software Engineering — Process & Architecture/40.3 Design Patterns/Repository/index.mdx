If you write raw SQL queries directly inside your Business Logic classes, your business rules are mathematically permanently coupled to that specific SQL dialect.

## 1. The Collection Illusion
The Repository pattern solves this by tricking the Business Logic into thinking the Database is just a simple, in-memory Array.
The architect creates an interface: `IUserRepository` with methods like `findById(id)` and `save(User u)`.
The Business Logic simply executes: `User u = repository.findById(42);`.

## 2. Isolating the SQL
The actual concrete implementation (`PostgresUserRepository`) mathematically implements the interface and hides all the ugly JDBC/SQL logic inside it.
This provides two massive architectural advantages:
1. **Testing**: You can create an `InMemoryUserRepository` for Unit Tests, completely bypassing the physical database.
2. **Swapping**: If the company migrates from PostgreSQL to MongoDB, you simply write a `MongoUserRepository` class. You do not have to mathematically alter a single line of your core Business Logic.
