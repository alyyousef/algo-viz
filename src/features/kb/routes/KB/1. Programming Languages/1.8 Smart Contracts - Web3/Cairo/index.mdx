**Cairo** was created by StarkWare in 2020. 

To understand Cairo, you must understand the Ethereum scaling problem. Ethereum can only process about 15 transactions per second because every single node on earth must mathematically re-execute every transaction to verify it. 
StarkWare invented **Starknet** (a Layer 2 Rollup). Instead of executing transactions on Ethereum, they execute a million transactions on a massive off-chain supercomputer. The supercomputer mathematically generates a single, tiny cryptographic proof (a STARK) proving that all 1 million transactions were executed correctly, and submits only that tiny proof to Ethereum.

Cairo (CPU Algebraic Intermediate Representation) is the programming language used to write those programs. It is the first Turing-complete language explicitly designed to mathematically prove that its own execution was correct.

## 1. Deep Dive & Mechanics

Cairo is defined by its **Algebraic Virtual Machine**.

In a standard CPU (like x86), memory can be overwritten at any time. Cairo runs on a totally different mathematical architecture. Memory in Cairo is **Immutable** and heavily restricted by polynomial equations. Once you write to a memory address in Cairo, it mathematically cannot be changed. 

If you want to update a variable, you don't overwrite it; you recursively pass a brand new memory pointer to the next function. This mathematical immutability is an absolute requirement for the cryptography engine to generate the STARK proof.

## 2. Mathematical / Theoretical Foundation

Cairo relies on **Polynomial Commitments and Arithmetization**.

When you compile a Cairo program, the compiler does not generate assembly code. It mathematically translates your `if` statements and `for` loops into a massive system of polynomial equations (Arithmetization). 

When the program runs, the Cairo Virtual Machine generates an Execution Trace (a massive grid of numbers). The Prover then mathematically applies the STARK cryptographic protocol to this grid, compressing the execution trace into a tiny proof. Because of the mathematics of polynomials, anyone can verify this proof in milliseconds, even if the original program took 5 days to run.

## 3. Real-World Implementation

Here is an example demonstrating Cairo 1.0 syntax. (Note: The original Cairo 0 was incredibly difficult to write and looked like low-level assembly. Cairo 1.0 was rewritten in 2023 to be mathematically and syntactically almost identical to **Rust**).

```rust
// 1. Cairo 1.0 is heavily inspired by Rust
// We use the #[starknet::contract] macro to tell the compiler this is a Smart Contract
#[starknet::contract]
mod SimpleCounter {
    // 2. Storage Definition
    // We mathematically define the state variables that will be stored on the Starknet blockchain
    #[storage]
    struct Storage {
        counter: u256,
        owner: felt252, // Field Element (The native mathematical type of Cairo)
    }

    // 3. Events (Logging)
    #[event]
    #[derive(Drop, starknet::Event)]
    enum Event {
        CounterIncremented: CounterIncremented,
    }

    #[derive(Drop, starknet::Event)]
    struct CounterIncremented {
        new_val: u256,
    }

    // 4. Constructor (Initialization)
    // Runs mathematically exactly once when the contract is deployed.
    #[constructor]
    fn constructor(ref self: ContractState, initial_owner: felt252) {
        // We write to the blockchain storage using the 'write' method
        self.counter.write(0);
        self.owner.write(initial_owner);
    }

    // 5. External Functions (Transactions)
    // The #[abi(embed_v0)] macro makes this function callable from the outside world.
    #[abi(embed_v0)]
    impl CounterImpl of super::ICounter<ContractState> {
        
        // 'ref self: ContractState' allows the function to mutate the blockchain state
        fn increment(ref self: ContractState) {
            // Read the current state
            let current = self.counter.read();
            
            // Mathematically increment (checking for overflow automatically)
            let new_val = current + 1;
            
            // Write it back to the blockchain
            self.counter.write(new_val);
            
            // Emit an event to the blockchain logs
            self.emit(Event::CounterIncremented(CounterIncremented { new_val }));
        }

        // 'self: @ContractState' mathematically enforces that this is a READ-ONLY function
        fn get_count(self: @ContractState) -> u256 {
            // Because it's the last line, we omit the semicolon to return the value (Rust style)
            self.counter.read()
        }
    }
}
```

## 5. Interview Prep

**Q: What is a `felt252`?**
**A:** In standard languages, the base type is an integer (`u32`, `i64`). In Cairo, the base mathematical type is a **Field Element** (`felt252`). It represents an integer in the range $0 \le x < P$, where $P$ is a massive prime number (specifically, a 252-bit prime). Because STARK cryptography relies entirely on finite field arithmetic, all math in Cairo fundamentally occurs modulo this massive prime number.

**Q: Why was Cairo 0 rewritten into Cairo 1.0?**
**A:** Cairo 0 was a low-level, non-deterministic language. If you wrote a bug, the program wouldn't fail gracefully; it would just mathematically fail to generate a proof, halting the entire rollup. Cairo 1.0 (built on the *Sierra* intermediate representation) mathematically guarantees that a program will *always* successfully prove its execution, even if the execution results in a `panic!` or error, ensuring the blockchain never freezes.

**Q: How does Cairo compare to Solidity?**
**A:** Solidity is designed for the Ethereum Virtual Machine (EVM), which executes code on every node globally. Cairo is designed for the Cairo Virtual Machine (CVM), which executes code on *one* massive off-chain Prover, generates a mathematical proof, and sends the proof to Ethereum. Cairo scales infinitely better, but has a much steeper mathematical learning curve.

## 6. Production Use Cases

Cairo is the exclusive language for the StarkWare ecosystem (currently valued in the billions):
- **Starknet Decentralized Exchanges (DEXs):** High-frequency trading on Ethereum is impossible because transaction fees cost $10+. Platforms like *JediSwap* are written entirely in Cairo. They process thousands of trades per second off-chain, generate a STARK proof of the trades, and settle them on Ethereum for fractions of a penny.
- **Fully On-Chain Gaming:** Games like *Realms* or *Influence* require massive amounts of mathematical computation (pathfinding, combat physics) that are physically impossible on Ethereum Layer 1. These game engines are written in Cairo, allowing players to execute complex blockchain transactions with zero lag while maintaining full cryptographic security.
- **Enterprise ZK-Rollups (StarkEx):** Massive companies (like the derivative exchange dYdX or the NFT platform Sorare) do not use the public Starknet. They use Cairo to write their own private, custom App-Chains (StarkEx). They use Cairo to mathematically define their specific financial matching engines, drastically lowering their infrastructure costs while borrowing Ethereum's base layer security.

<Callout icon="info" title="The Sierra Intermediate Representation">
The magic of Cairo 1.0 is **Sierra** (Safe Intermediate Representation). When you compile Cairo 1.0, it turns into Sierra. Sierra is mathematically guaranteed to be free of infinite loops and undefined behavior. The Starknet Sequencer accepts the Sierra code, mathematically verifies its safety in milliseconds, and *then* compiles it down to the raw Cairo Assembly (CASM) for execution.
</Callout>
