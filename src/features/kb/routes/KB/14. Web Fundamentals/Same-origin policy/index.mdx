The **Same-Origin Policy (SOP)** is the foundational security boundary of the modern web. Without it, the internet would be a lawless wasteland where any website could steal data from any other open tab.

## 1. Defining an "Origin"
An Origin is strictly defined as the mathematical combination of three things:
**Scheme + Hostname + Port**.

## 2. What does SOP restrict?
SOP places ironclad walls between different origins within the browser:
1. **DOM Access**: An iframe loading `evil.com` cannot use JavaScript to read the DOM or keypresses of the parent window `bank.com`.
2. **Data Storage**: A script on `origin-a.com` is mathematically barred from reading the LocalStorage, IndexedDB, or Cookies belonging to `origin-b.com`.
3. **Network Requests**: AJAX/Fetch requests to different origins are blocked from reading the response (unless relaxed by CORS headers).

## 3. Exceptions to SOP
SOP intentionally allows certain cross-origin interactions because the web would be unusable without them:
- **Linking**: You can freely embed `<img src="different-origin.com/image.jpg">`.
- **Scripts**: You can load `<script src="cdn.com/react.js">`. (However, the script executes entirely within the context and permissions of the *hosting* page).


<Callout icon="tip" title="PostMessage">


If you legitimately need two different origins to communicate (e.g., a secure payment iframe communicating with the parent e-commerce site), you must use the strict `window.postMessage()` API. This allows controlled, explicitly verified message passing across the SOP boundary.
