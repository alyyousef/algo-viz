<ConceptTemplate title="syslog">

Before `systemd` and binary logs took over, the standard for Linux logging was **syslog** (handled by daemons like `syslogd` or `rsyslog`). 

`syslog` is both a protocol and a daemon. It listens for log messages generated by the Kernel or user-space applications and routes them to specific plain-text files inside `/var/log/` based on a set of rules defined in `/etc/syslog.conf`.

## Facilities and Severities

Every syslog message is tagged with two pieces of metadata:
1. **Facility**: What type of program generated the log (e.g., `auth` for security, `mail` for email, `cron` for scheduled tasks, or `local0-7` for custom apps).
2. **Severity**: How bad is it? (e.g., 0=Emergency, 3=Error, 6=Info, 7=Debug).

<Callout icon="info" title="Remote Logging">
  The greatest strength of `syslog` is its built-in network capability. You can configure `rsyslog` on 50 different web servers to forward all their logs over UDP Port 514 to a single, centralized "Syslog Server". This ensures that if a web server is hacked and deleted, the logs of the hack are safely preserved on a different machine.
</Callout>

## Modern Compatibility
Even though `systemd-journald` is the default on modern Linux, `rsyslog` is usually still installed alongside it. `journald` acts as the primary collector, and then quietly forwards a copy of all the logs to `rsyslog` so that the traditional plain-text files in `/var/log/` continue to function for legacy monitoring tools.
