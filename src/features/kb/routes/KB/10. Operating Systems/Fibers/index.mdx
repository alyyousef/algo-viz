**Fibers** (also known as Green Threads, Coroutines, or User-Mode Threads) represent a fundamental architectural bypass of the Operating System.

If you build a web server and you want to handle 1,000,000 simultaneous users, you cannot spawn 1,000,000 OS Threads. 
An OS Thread is a massive, mathematically heavy object. It requires the OS kernel to allocate megabytes of physical RAM for the stack, and every time the OS switches between threads, it triggers an incredibly expensive hardware Context Switch (flushing CPU caches). 1,000,000 OS Threads will mathematically crash any server on earth due to out-of-memory errors and context-switch thrashing.

Fibers solve this. A Fiber is a thread that is mathematically managed by the *Application*, not the OS. The Operating System has absolutely no idea that Fibers exist. 

## 1. Deep Dive & Mechanics

Fibers are defined by **Cooperative Multitasking** and **M:N Scheduling**.

- **Preemptive (OS Threads):** The OS uses a hardware timer to violently pause a thread, whether it wants to be paused or not, to let another thread run.
- **Cooperative (Fibers):** Fibers are polite. A Fiber runs until it reaches a mathematical stopping point (like waiting for a database response). The Fiber explicitly calls `yield()`. This function instantly saves its own registers and jumps to the next Fiber.

Because this context switch happens entirely in User-Space without ever talking to the OS Kernel (avoiding Ring 0 transitions and hardware interrupts), switching Fibers takes nanoseconds instead of microseconds.

## 2. Mathematical / Theoretical Foundation

The mathematical power of Fibers relies on **The M:N Scheduler Model**.

In standard programming (1:1 Model), 1 Application Thread maps directly to 1 OS Thread.
In Fiber programming (M:N Model), the Application Runtime maps **M** Fibers onto **N** OS Threads. 

If you have a 4-core server, the Runtime (like the Go Scheduler) spawns exactly 4 massive OS Threads (one for each physical CPU core). It then mathematically multiplexes 1,000,000 tiny Fibers onto those 4 OS Threads. When Fiber 1 issues an HTTP request, the Runtime puts Fiber 1 to sleep, grabs Fiber 2, and executes it on the same OS Thread, ensuring the physical CPU never stops mathematically calculating.

## 3. Real-World Implementation

Here is a conceptual demonstration of how a Fiber/Coroutine architecture works under the hood. While you normally use high-level languages like Go (`go func()`) or Python (`async/await`), this shows the raw mathematical C/Assembly logic required to perform a User-Space Fiber swap.

```c
#include <stdio.h>
#include <setjmp.h> // The standard C library for saving CPU states

// 1. The Fiber Context Structure
// We need a place to save the physical CPU registers for this specific Fiber.
// jmp_buf is a mathematical array that holds the CPU state.
typedef struct {
    jmp_buf context;
    int is_running;
} Fiber;

Fiber fiber_A, fiber_B;
Fiber* current_fiber;

// 2. The Cooperative Yield Function
// This is the absolute core of Fiber architecture.
void fiber_yield(Fiber* next_fiber) {
    Fiber* previous = current_fiber;
    current_fiber = next_fiber;

    // setjmp() mathematically saves the physical CPU registers (Stack Pointer, 
    // Program Counter) into the previous Fiber's context buffer.
    // It returns 0 when saving. It returns 1 when resumed by longjmp.
    if (setjmp(previous->context) == 0) {
        
        // longjmp() mathematically rips the registers out of the next_fiber's buffer
        // and shoves them physically into the CPU. The CPU instantly jumps into
        // the code of the new Fiber. NO OS KERNEL INVOLVED.
        longjmp(next_fiber->context, 1);
    }
}

// 3. The Fiber Execution Logic
void run_fiber_A() {
    printf("Fiber A: Starting...\n");
    
    // Fiber A hits a blocking operation (like waiting for a network packet).
    // Instead of blocking the OS Thread, it explicitly yields control to Fiber B.
    printf("Fiber A: Yielding to Fiber B...\n");
    fiber_yield(&fiber_B);
    
    printf("Fiber A: Resumed! Finishing work.\n");
}

void run_fiber_B() {
    printf("Fiber B: Starting...\n");
    
    // Fiber B finishes its work and yields control back to Fiber A.
    printf("Fiber B: Yielding to Fiber A...\n");
    fiber_yield(&fiber_A);
}
```

## 5. Interview Prep

**Q: If Fibers are so mathematically fast, why do we use OS Threads at all?**
**A:** **Blocking System Calls.** If a Fiber issues a blocking read to the hard drive (`read()`), the Operating System halts the *entire physical OS Thread*. Because the OS doesn't know Fibers exist, all 10,000 Fibers mapped to that OS Thread are instantly mathematically frozen and destroyed until the hard drive responds. Language runtimes (like Go or Node) must use massive, complex non-blocking asynchronous architectures (like `epoll` or `io_uring`) to mathematically intercept blocking calls and prevent the OS from freezing the thread.

**Q: What is the difference between a Fiber, a Goroutine, and Async/Await?**
**A:** Conceptually, they are all User-Space cooperative multitasking architectures.
- **Fibers / Green Threads:** Historically full implementations of threads in user-space (like early Java Green Threads or Ruby before 1.9).
- **Goroutines (Go):** Highly optimized, stack-growing Fibers mapped via an M:N scheduler. They are incredibly memory-efficient (starting at just 2KB of RAM).
- **Async/Await (Python/C#/JS):** Syntactic sugar over a State Machine. Instead of saving raw CPU registers (like C `setjmp`), the compiler mathematically translates your function into a switch-case state machine, pushing local variables onto the heap to simulate yielding.

**Q: Why did Java remove Green Threads in version 1.3, but bring them back in Java 21 (Virtual Threads)?**
**A:** In 1998, most computers only had 1 physical CPU core. Green Threads were great. But as multi-core processors became standard, early Green Threads could not mathematically spread across multiple cores, so Java abandoned them for OS Threads (1:1). However, as cloud servers (handling millions of microservice API calls) emerged, OS Threads proved too heavy. Java 21 introduced **Virtual Threads**, a modern M:N scheduler capable of spreading millions of Fibers across massive multi-core cloud servers.

## 6. Production Use Cases

Fiber architectures completely dominate high-throughput, network-bound modern backend engineering:
- **Go Web Servers (Docker / Kubernetes):** The Go programming language was mathematically designed around the Goroutine (Fiber). When you write a Go web server, every single incoming HTTP request automatically spawns a new Goroutine. Because they only take 2KB of memory and context switch in nanoseconds, a single cheap AWS server running Go can mathematically handle hundreds of thousands of concurrent WebSocket connections simultaneously without sweating.
- **Erlang / Elixir (WhatsApp / Discord):** Erlang was built in the 1980s by Ericsson to manage telecom switches. It uses an incredibly advanced Actor Model based entirely on millions of micro-processes (Fibers). When WhatsApp was acquired by Facebook for $19 Billion, their backend had only 50 engineers. They mathematically achieved this by running Erlang, utilizing millions of Fibers to route billions of chat messages across massive clusters with zero OS Thread overhead.
- **Video Game Engines (Naughty Dog / DOOM):** Modern AAA video games (like The Last of Us) must calculate Physics, AI, Animation, and Audio in exactly 16.6 milliseconds to hit 60 FPS. If they used OS Threads, the context switching overhead would cause the game to stutter. Game engines implement massive, highly customized C++ Fiber Job Systems. They spawn exactly 8 OS Threads (for an 8-core console) and mathematically dispatch thousands of micro-Fibers (e.g., "Calculate bullet trajectory") into a lock-free queue, ensuring the CPU cores are utilized at 100% mathematical efficiency.

<Callout icon="warning" title="The Stack Size Problem">
An OS Thread is safely allocated 8 Megabytes of RAM for its Stack (local variables). If a Fiber is only allocated 2 Kilobytes (to save memory), what happens if you write a deep mathematical recursive function? A standard Fiber will instantly hit a Stack Overflow and crash the program. Go solved this by implementing **Contiguous Stacks**—the runtime mathematically tracks the stack pointer, and if it gets too close to the end, it pauses the Fiber, allocates a massive new chunk of RAM, copies the data over, and updates all the pointers flawlessly.
</Callout>
