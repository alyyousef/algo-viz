Imagine you have a single `main.tf` file that defines a web server. You want to deploy this exact server to both a "Development" AWS account and a "Production" AWS account. If you just run `terraform apply` twice, the second run will mathematically overwrite the state of the first run.

## 1. Mathematical State Isolation
Workspaces solve this by isolating the state file.
When you type `terraform workspace new prod`, Terraform creates a completely separate, mathematically isolated state file bucket (e.g., `terraform.tfstate.d/prod`).
When you are in the `prod` workspace, any changes you make mathematically only apply to the `prod` state file. You can switch to the `dev` workspace, and Terraform physically ignores the `prod` infrastructure, allowing you to use the exact same HCL code to manage parallel universes.

## 2. Dynamic Code Execution
Terraform exposes the current workspace name via a mathematical variable: `terraform.workspace`.
You can use this to mathematically alter the deployment based on the environment:
```hcl
resource "aws_instance" "web" {
  instance_type = terraform.workspace == "prod" ? "m5.large" : "t3.micro"
}
```
If you are in the `prod` workspace, it provisions a massive server. If you switch to the `dev` workspace, it automatically provisions a tiny server to save money, all from the same codebase.
