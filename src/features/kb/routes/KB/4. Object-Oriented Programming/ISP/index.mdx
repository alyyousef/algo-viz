Imagine a massive interface called `IMachine` that contains three methods: `print()`, `scan()`, and `fax()`.

## 1. The Fat Interface Problem
If a developer builds a simple `BasicPrinter` class, they must mathematically implement `IMachine`.
Because they signed the contract, the compiler forces them to write a `fax()` method. But a basic printer cannot fax. The developer is mathematically forced to write `public void fax() { throw new Error("Not Supported"); }`. This is a violation of the Interface Segregation Principle. The code is now lying to the compiler.

## 2. Mathematical Segregation
ISP solves this by mathematically fracturing the fat interface into hyper-specific micro-contracts.
You create three distinct interfaces: `IPrinter`, `IScanner`, and `IFax`.
The `BasicPrinter` class only implements `IPrinter`.
An `AdvancedMultiFunctionPrinter` class implements all three: `implements IPrinter, IScanner, IFax`.
By segregating the interfaces, you mathematically guarantee that classes only depend on the exact behaviors they actually possess, eliminating "Not Supported" runtime exceptions entirely.
