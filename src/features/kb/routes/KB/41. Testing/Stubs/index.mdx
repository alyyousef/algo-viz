When isolating a class for a Unit Test, you must mathematically sever its connection to external dependencies. A Stub is the simplest, "dumbest" way to do this.

## 1. The Brainless Double
A Stub contains absolutely no mathematical logic. It does not contain variables. It does not check arguments. It simply returns a fixed, hardcoded value.
Imagine testing a `CheckoutService` that depends on an `IWeatherAPI`. You do not want the test to fail just because it's raining outside.
```java
class SunnyWeatherStub implements IWeatherAPI {
    // Mathematically ignores the zipcode argument
    public String getWeather(int zipcode) {
        return "SUNNY";
    }
}
```
You inject the `SunnyWeatherStub` into the test. The test is now mathematically deterministic; it will always execute the "sunny day" logic.

## 2. Stubs vs Mocks
- A **Stub** provides data *to* the system under test (State Verification). You use a Stub to force the code down a specific mathematical `if/else` path.
- A **Mock** verifies that the system under test called the dependency correctly (Behavior Verification). You use a Mock to assert that `emailService.send()` was mathematically executed exactly one time.
